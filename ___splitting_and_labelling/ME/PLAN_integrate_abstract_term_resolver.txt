0) WHAT ALREADY EXISTS  — read this first, half the job is done
--------------------------------------------------------------------------------

_abstract_term_resolver.py (504 lines) ALREADY DOES the hard part:

    MODELS               4 coreference models with accuracy weights
                         maverick-ontonotes .836 / maverick-preco .820 /
                         lingmess .814 / maverick-litbank .780
    run_model()          run one of them over raw TEXT -> clusters of char spans
    find_cluster()       the cluster that IS this pronoun
    pick_antecedent()    the best answer in that cluster
                         (before the pronoun > named > short > long)
    mention_name()       render it:  "a technician named Gustav Holm"
                                     -->  "Gustav Holm"
    merge_votes()        fold the 4 models' answers, combine their weights
    deictic_label()      "I"/"we" -> "the narrator",  "you" -> "the viewer"
    possessive()         "its windscreen"  -->  "the tractor's windscreen"
    build_canonical_map()  one label per entity, document-wide
    canonical_key()

_visualisables_extractor.py ALREADY CALLS six of those (resolve_references,
assign_identities). So this is NOT a from-scratch integration. It is:
    * finishing the resolver's public API, and
    * moving the coreference OUT of the per-segment loop, where it is both
      slower and less accurate than it needs to be.

THE THREE REAL GAPS
  a) THE FUNCTION myownstuff.py IMPORTS DOES NOT EXIST.
     myownstuff.py:61  from abstract_term_resolver import resolve_all_abstract_terms
     Wrong twice over: the module is now _abstract_term_resolver, and that
     function was never written. It exists only as an empty stub in
     old_abstract_term_resolver.py. All of the resolver's orchestration is
     locked inside main(), which reads a FILE, PRINTS, and returns nothing.

  b) THE EXTRACTOR REIMPLEMENTS main() BADLY.
     _model_referent() takes the FIRST model that answers, in weight order.
     main() takes a WEIGHTED VOTE of all four, with merge_votes() folding
     answers that contain one another, and a real confidence out of it
     (score / total_weight). The extractor instead hardcodes 0.75 for "a
     model said so" and 0.10 for "recency". It also ignores deictic_label()
     and possessive() entirely, and CONFIDENCE_THRESHOLD (0.25) is unused.

  c) THE MODELS RUN PER SEGMENT.
     Since the API became one-segment-at-a-time, _coref_clusters() fires on
     every call whose segment contains a pronoun. Measured: ~5 s for lingmess
     alone, ~51 s for all four. A script with 20 pronoun-bearing segments is
     therefore 20 x 5 s = 100 s of model time for the WEAKEST setting.
     Running all four ONCE, up front, is 51 s and more accurate.
     -> this is the whole argument for doing it as a stage before.


--------------------------------------------------------------------------------
THE DESIGN DECISION — pass a MAP as a param. Never pass rewritten text.
--------------------------------------------------------------------------------
This answers the question in the phase-2 note ("perhaps pass the map as an
initial thing? so pass abstract map as a param?"). Yes — a map, and here is
why it can only be a map:

The resolver's own main() ends by REWRITING the script:
    "It was once covered"  -->  "[the valley] was once covered"
That output is for a human to read. It must never be fed to the extractor:

    * it changes the string, so every character offset moves, and char
      offsets are what build the template ("[1] was once [2]")
    * the template is what the video puts ON SCREEN. Substituting the text
      would put "the valley was once covered" on screen when the script
      says "It was once covered". Wrong words, wrong timing.
    * the pronoun is still the thing the viewer hears. We want to KNOW it
      means the valley, not to pretend it was never said.

So the contract is:

    resolve_all_abstract_terms(text) -> {(start_char, end_char): {...}}

keyed by where the pronoun IS, not by what it should say. The extractor
already keeps every pronoun as a KIND_REFERENCE slot with its token span —
that is the hook this plugs into.


--------------------------------------------------------------------------------
THE ORDER THINGS RUN IN  (myownstuff.py)
--------------------------------------------------------------------------------
    0) split the script into line segments          (already done, elsewhere)

    1) abstract_terms = resolve_all_abstract_terms(<the whole script>)
       ONCE per script. ~51 s, all four models.        <-- NEW, step 2 below

    2) for each segment:
           visualisables_data = get_visualisable_data(
               segment, previous_segments, next_segment,
               abstract_terms=abstract_terms)         <-- NEW param, step 4

So: resolve first, extract second. The visualisables code then never runs a
coreference model at all — it looks the answer up.

STEP 2 — agree on ONE text, so the char offsets line up
        FILES: _visualisables_pipeline.py, myownstuff.py
  THIS IS THE MAIN HAZARD. The map is keyed by char offsets into whatever
  text the resolver was given. The pipeline builds its doc by joining the
  segments it was handed — normalised whitespace, and only a PREFIX of the
  script. Those two coordinate systems must be identical or every lookup is
  silently off by a few characters.
  - Expose the pipeline's joining rule as a shared helper:
        join_segments(segments) -> " ".join(" ".join(s.split()) for s in segments)
    _parse_together() already does exactly this inline. Lift it out.
  - myownstuff.py builds the map over join_segments(ALL segments).
  - The property that makes this safe: joining is left-to-right with single
    spaces, so the join of a prefix IS a prefix of the join. Every per-segment
    call therefore agrees with the full-script offsets.
  DONE WHEN: for every i,
        join_segments(segments[:i]) == join_segments(segments)[:len(...)]
    asserted in a throwaway check over script-whales / script-rome /
    script-spices. If this ever fails, fall back to keying the map by
    (segment index, pronoun index within segment) instead of char offsets.

STEP 3 — one parse, or two? DECIDE AND WRITE IT DOWN
  The resolver's main() loads en_core_web_trf. The extractor uses
  en_core_web_sm (via shared_text_logic, one shared model). Two different
  parses of the same text.
  - This is FINE as long as the only thing crossing between them is CHARACTER
    OFFSETS and STRINGS — which is what the map is. The coreference models
    themselves take raw text, not a Doc.
  - Do NOT pass a Doc, a Token or a token index across the boundary. sm and
    trf tokenise differently (measured earlier: trf lost Molly/PERSON, sm
    kept it).
  - Cheaper option worth measuring first: have resolve_all_abstract_terms()
    accept an optional doc so it can reuse the sm parse, and check whether
    the answers change. If they do not, drop trf and save the second parse.
  DONE WHEN: the choice is recorded in the resolver's docstring with a
    measurement next to it.

--------------------------------------------------------------------------------
AFTER THAT — the "wishy washy terms" BONUS from myownstuff.py
--------------------------------------------------------------------------------
    "The yellow and black guy flew away."  -->  "The [bee] flew away"

Worth knowing before anyone builds this: THE CLUSTERS ALREADY CONTAIN IT.
Coreference clusters hold every mention of an entity, not just its pronouns
— "the yellow and black guy" and "a bee" land in the same cluster. The
resolver simply never asks, because main() only targets PRP/PRP$ tokens:

    toks = [t for t in doc if t.tag_ in ("PRP", "PRP$")]

So this needs NO new model and no LLM. It needs a wider target list: also
take definite noun phrases whose head is a GENERIC_TOPIC_NOUN ("guy",
"thing", "man") — shared_text_logic already has that list, and the
extractor already drops those nouns as unfilmable in drop_non_visualisable().
The two facts fit together exactly: the nouns we throw away for having no
picture are the ones whose picture is in the cluster.

Do this as a separate stage, after the six steps above are working.


--------------------------------------------------------------------------------
WHAT NOT TO DO
--------------------------------------------------------------------------------
  * Do not feed the resolver's rewritten text to the extractor. See THE
    DESIGN DECISION.
  * Do not call an LLM for this yet. old_abstract_term_resolver.py's step 2
    sketched that, and it is a reasonable fallback for what the four models
    all miss — but they are benchmarked (81-84 F1) and already cached
    locally, so measure what is actually left over before adding a network
    call to a per-script batch job.
  * Do not run coreference per segment once step 4 lands. If both paths are
    live, the per-segment path is the fallback for callers who did not build
    a map, not something to run alongside.
  * Do not let the extractor import spaCy models of its own. One shared sm
    model, reached through shared_text_logic. That invariant is the reason
    the per-segment pass is cheap.
